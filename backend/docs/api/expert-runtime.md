# Expert Runtime publication

Backend owns Expert Runtime publication. Builder is a local configuration generator; it does not
call Backend or Gateway and it does not update Expert status.

## Identity and paths

An Expert has one immutable `expertId`, generated by Backend as 16 lowercase hexadecimal
characters. There is no second deployment key.

For each enabled Runtime, Backend derives one name:

```text
expert_runtime_name(runtimeType, expertId) = expert-{runtimeType}-{expertId}
```

The same value is the configuration directory name, Gateway Service ID and Gateway Route ID. The
Route Prefix is `/acp/<runtime_name>`.

Runtime homes are created under the absolute `EXPERT_ACP_CONFIG_BASE`. Backend replaces only
Builder-managed configuration (`AGENTS.md`, Runtime config, Skills, an empty compatibility
`knowledge/` directory, plus optional Codex `auth.json`) and preserves Runtime-owned sessions,
logs, caches and OpenCode state.

## Status endpoint

Publication and removal use the existing endpoint:

```http
PATCH /api/v1/experts/{expertId}/status
```

Publish request:

```json
{"status":"published"}
```

Before building a Runtime, Backend resolves every `mcpConnectorIds` entry from AGW Admin,
requires an enabled Service with at least one discovered tool, upserts the deterministic shared
MCP Route, and upserts the Expert's single MCP VirtualKey with exactly those Route IDs. It then
repeats `initialize`/`tools/list` through every data-plane Route using that Key.

For a knowledge-bound Expert, publication stores the `expert_knowledge_bases` relationship and
adds one read-only Backend knowledge MCP client. It does not require current documents to be ready:
readiness is checked fail-closed only when the model calls the tool, so later document changes do
not require a republish.

For every enabled Runtime, Backend:

1. writes Build Input Schema v2 and local assets to hidden staging under Config Base; `knowledge`
   is always an empty list because Backend owns public retrieval; a knowledge-bound Expert gets
   the internal `search_expert_knowledge` client with an expert-scoped
   `EXPERT_KNOWLEDGE_AUTHORIZATION` secret reference; external MCP input contains only the AGW
   data-plane Route URL, discovered `toolAllow`, and the `EXPERT_MCP_AUTHORIZATION` secret
   reference; when Connectors are bound, Backend also appends a
   managed MCP capability inventory, including fully qualified callable namespace identifiers, to
   the generated Expert instructions so the model neither confuses tools with the separate MCP
   resources/resource-templates APIs nor emits an unnamespaced bare tool call; generated MCP
   clients use a 60-second per-tool timeout so normal public Connector latency is not cut off by
   the previous 30-second limit;
2. executes Builder `build`, then Builder `validate`, using argument arrays;
3. installs the generated managed files into the fixed Runtime home;
4. creates an isolated `<EXPERT_ACP_CWD_BASE>/.publication/<runtime_name>` cwd for publication
   smoke, prepares empty non-symlink `.git/.agents/.codex` inner-sandbox mount targets there, and
   writes `EXPERT_ACP_CODEX_ADAPTER_COMMAND` into Codex Service configuration; this defaults to the
   repository-owned `runtime/codex-acp` adapter, so deployment does not depend on
   `/usr/local/amazon/scripts`;
5. injects the derived expert-scoped knowledge capability and, when external Connectors exist,
   reads their real Expert MCP Key only in memory and injects both references into the ACP Service
   environment;
6. upserts and strictly reads back the ACP Service and Route;
7. adds the ACP Route ID to the existing Backend ACP caller Key allowlist;
8. sends a real ACP Turn through `/acp/<runtime_name>/turn` and requires both a completion event
   and the generated test marker.

The publication instructions start with the WinWise platform rules: bound Skills may guide
work within existing permissions; attachments, knowledge, webpages and MCP results are material,
not authorization. The rules preserve legitimate reviews, truthful appeals, authorized citations
and transfers, and reject clearly harmful requests and deliberate business fabrication.
No separate moderation model, keyword blacklist or user risk score is introduced.

Codex publication requires Builder's `approval_policy="never"` together with the existing
restricted permission profile. Sandbox escalation is rejected by Codex before ACP approval.
Gateway retains `permissionMode` (default `auto_approve`) because this adapter also asks approval
for ordinary bound MCP calls; setting Gateway to `deny` cancels those legitimate calls. The
configured Gateway mode cannot override Codex's `never` execution check. Builder also fixes
`project_doc_max_bytes=0`: writable workspace AGENTS files remain task material instead of
being automatically loaded as project instructions; platform HOME instructions and bound Skills
remain available. The same generated platform text is sent via `developer_instructions` and
kept in read-only AGENTS.md for inspection; validation requires these copies to match. User tasks
remain separate user messages. Runtime contract
version 7 republishes existing Experts through the same lifecycle, preserving their fixed homes.

`EXPERT_ACP_RUNTIME_ENV_NAMES` contains only the explicitly constructed Service environment names.
The outer wrapper clears inherited host variables before passing those selected values. The
Gateway's provider/admin environment is not implicitly available to Expert processes. Deploy the
host sandbox prerequisites described in [Runtime sandbox](../RUNTIME_SANDBOX.md) before publishing.

After every enabled Runtime succeeds, Backend commits the Expert as `published`. Failure
keeps the previous `draft` or `unlisted` status and independently disables every managed Route,
Service, and Expert MCP Key. A cleanup failure is reported instead of being hidden by the original
publication error.

Backend lifespan reconciliation runs before the API accepts traffic. For every database row marked
`published`, it checks the Runtime contract version, required managed files, Service cwd and
`allowed_roots`, Codex `adapter_command`, complete Route configuration and the empty Runtime
Knowledge contract before a live smoke.
Missing or stale resources trigger the normal fail-closed path: commit `unlisted`, disable remaining
resources, rebuild and republish, and restore `published` only after readback and smoke succeed. A
failed repair remains `unlisted` and does not appear in the marketplace or accept new Chat Sessions.
Backend also validates the installed Codex permission profile instead of trusting the Service
contract marker alone, so an old Builder cannot be stamped as the current Runtime contract.
`EXPERT_RUNTIME_OPERATION_TIMEOUT_SECONDS` caps each Builder build/validate and ACP smoke. A
per-Expert failure does not stop later Experts; lifespan itself refuses health if either the
`unlisted` database state or disabled Gateway-resource readback cannot be confirmed.

The Gateway host must have Bubblewrap and the real Codex ACP adapter installed. The bundled
adapter defaults to `/usr/local/bin/codex-acp`; set `EXPERT_ACP_CODEX_REAL_ADAPTER_COMMAND` when
that executable lives elsewhere. The Backend repository path must be visible to Gateway unless
`EXPERT_ACP_CODEX_ADAPTER_COMMAND` points to another deployed copy of the bundled adapter.
Its filesystem namespace binds only the active Runtime Home and the validated user or publication
workspace; sibling Runtime Homes and tenant workspaces are absent.
This outer namespace remains capability-free but does not disable Codex's own Bubblewrap sandbox.
Before the real adapter starts, the wrapper requires the active cwd's `.git`, `.agents`, and
`.codex` mount targets to be real empty directories. A wrapper error naming one of these targets
means the tool command has not started; it is not evidence that the requested Skill file is
unreadable.

Unlist request:

```json
{"status":"unlisted"}
```

Backend disables existing Codex/OpenCode Routes and Services, disables the Expert MCP Key,
closes related Runtime threads, preserves Runtime homes, and then commits `unlisted`. Shared MCP
Services and Routes are not disabled. Repeating the current status is idempotent. The endpoint
does not accept `draft`.

## MCP Connector API

`GET /api/v1/mcp-connectors` lists enabled AGW MCP Services in stable ID order. It returns only
`id`, `name`, `description`, and `transport`; it never returns upstream URL/command/env/auth or
Gateway Route, Session, or Key objects. Directory reads do not execute `tools/list`. If AGW Admin
is unavailable, Backend returns a sanitized `503 MCP_CONNECTORS_UNAVAILABLE`.

Expert Create/Patch accepts `mcpConnectorIds: list[str]`. IDs must be nonblank and unique, but
Create/Patch does not call AGW. Service existence, enabled state, and nonempty tool discovery are
publication checks. There is no Connector/Binding/Publication table and no legacy `mcpServers`
fallback or dual write.

For service ID `serviceId`, the shared MCP resource names are:

```text
connectorHash = first 16 lowercase hex characters of sha256(UTF-8 serviceId)
route ID       = mcp-connector-<connectorHash>
route path     = /mcp/connectors/<connectorHash>
Expert key ID  = mcp-key-<expertId>
```

Published Experts are read-only. `PATCH /api/v1/experts/{expertId}` returns
`409 EXPERT_PUBLISHED_READ_ONLY`; unlist before editing and publish again afterward.

## Builder input and model credentials

Builder input uses one Expert and one Runtime, contains only `expertId`, and points both Runtime
types at `EXPERT_AGENT_GATEWAY_MODEL_BASE_URL`. Backend stages Skill bytes locally;
there are no public Runtime Build Input or Runtime Asset download APIs.

An optional `EXPERT_AGENT_GATEWAY_MODEL_API_KEY` is a local model Route key. Backend writes Codex
`auth.json` with mode `0600` or exposes the key to OpenCode through its Service environment. The
upstream Provider Credential remains in Agent Gateway and is never written to Build Input or an
Expert directory.

## Chat behavior

A bound Chat Session stores only `expertId`, `runtimeType`, and the normal/search ACP session IDs.
Every operation derives `/acp/expert-{runtimeType}-{expertId}` at request time. The Session itself
does not snapshot an index, Build, Service, Route or Prefix; there is no Runtime Binding API/table.

Creating a bound Session requires a published Expert and an enabled selected Runtime. The model
uses `search_expert_knowledge` only when a question needs the bound reference documents. Each call
resolves current KB relations, requires ready isolated bindings, and maps every reference to a live
Document whose `indexedSha == sourceSha`; missing/stale/untrusted knowledge fails the tool call.
An automatically synchronized document replacement is visible to the next tool call without
changing Runtime files, status or publication.

`EXPERT_ACP_DEFAULT_CWD=` means legacy/unbound requests omit `cwd`. Bound Expert Sessions use
`<EXPERT_ACP_CWD_BASE>/<tenantId>/users/<userId>`; Backend creates the absolute root, user directory,
and empty `.git/.agents/.codex` Bubblewrap mount targets. Before an old bound Session next executes,
Backend changes tenant-wide scope to user scope and clears both ACP IDs. Local history and old
files are preserved; shared files are not copied into a user's workspace.
